=== September Week 1: K8s upgrade to 1.35.6 + Rancher via Gateway API — 20:53 18-07-2026 ===
Much bigger day than the plan called for. Started by checking real EOL
dates: the cluster (v1.31.4) had been out of upstream maintenance
support since Oct 2025, and Rancher's latest stable (2.14.3) only
certifies importing K8s 1.33-1.35 anyway. Bumped the pinned version in
Ansible (kubernetes-repo, kubeadm-init, runtime-tools defaults) to
1.35.6 and rebuilt the cluster from scratch instead of a 4-hop live
kubeadm upgrade (ADR-025) — 4/4 nodes Ready, Calico/kube-vip/MetalLB/
Envoy Gateway all healthy post-rebuild, docs/manual-bootstrap.md kept
in sync with the new version.
Installed Rancher 2.14.3 via Helm, exposed through a dedicated Gateway
API resource instead of reusing the smoke-test Gateway (ADR-026, which
gets regenerated from upstream on every 03_gateway_api_metallb.sh run).
Hit and fixed two install-time issues: ingress.tls.source defaulting
to cert-manager-based self-signed certs we don't have installed
(ADR-027), and Rancher's default 3 replicas restarting repeatedly on
the startup probe during first boot — tested whether replica count was
the actual cause (it wasn't; 3 replicas also stabilized fine given
time) and kept replicas=1 anyway as a RAM-budget choice, not a fix
(ADR-028).
Biggest chunk of the day was Windows-to-lab network access, which
turned into a real multi-layer investigation:
  1. Windows had no route to the Multipass bridge (10.215.138.0/24) —
     added one via the WSL2 VM as gateway.
  2. Multipass's own auto-generated iptables-legacy rules (separate
     from the ADR-009 rules, invisible to plain  because
     of the parallel legacy/nft stack on this WSL2 host) only allow
     ESTABLISHED/RELATED traffic back into the bridge by default —
     inserted a targeted ACCEPT rule for eth0->mpqemubr0.
  3. Got the request to the VM, but the VM's reply had no path back to
     the Windows-side source address (two hops + a NAT boundary away).
     Diagnosing that further (VM routing table, rp_filter) wasn't
     worth it for a personal lab — pivoted to an SSH local
     port-forward through cp-1 instead (scripts/rancher-tunnel.sh),
     which never leaves the WSL2 side of the network.
  4. The tunnel then hit Envoy Gateway's SNI matching on the Gateway's
     fixed hostname (rancher.lab) — localhost/127.0.0.1 sent the wrong
     SNI and got dropped immediately. Confirmed with
     curl --resolve rancher.lab:8443:127.0.0.1 (worked) vs bare
     127.0.0.1 (didn't). Fix: dropped the hostname field entirely from
     Gateway/rancher and HTTPRoute/rancher — only one backend on this
     Gateway anyway, hostname routing added friction with no benefit.
All of this is now ADR-029, and documented step-by-step as Phase G in
manual-bootstrap.md. scripts/pipeline/main.sh now also sources
04_rancher.sh, so a full rebuild includes Rancher automatically.
Status: Rancher UI reachable at https://localhost:8443/ via
scripts/rancher-tunnel.sh, local cluster auto-registered (addLocal
default) — satisfies the plan's "import" step for free. Fase 3
essentially closed, well beyond the original Week 1 scope.
Next: Day 5 — explore the Rancher UI (RBAC, deploy via UI vs kubectl),
then Week 2 — ArgoCD, which will need this exact same Gateway +
tunnel pattern again for its own UI.

=== ArgoCD via Helm/Artifact Hub, PC-restart networking saga, ADR-029 resolved — 10:45 19-07-2026 ===
Installed ArgoCD via the argo-helm chart (10.1.4, Artifact Hub-listed),
same Gateway+HTTPRoute pattern as Rancher, with a custom bcrypt admin
password set at install time instead of the auto-generated one
(ADR-030 established: from now on every *application* install goes
through a Helm chart sourced from Artifact Hub, matching the day-job
pattern; cluster infra like Calico/MetalLB stays grandfathered).
Retroactively confirmed Rancher already complied before the policy
existed (same rancher-stable repo as the one indexed on Artifact Hub).

Then the PC got restarted mid-session (VMs not destroyed first). What
followed was a long, genuinely useful debugging chain:
  1. kube-apiserver was crash-looping on cp-1 — traced to clock drift
     after the VMs resumed (timedatectl: "System clock synchronized:
     no"), which broke TLS between etcd/apiserver.
  2. Tried `multipass restart` on all 4 VMs to force a clean NTP sync.
     This actually triggered scripts/lab-management.sh's own health
     check gate, which failed on a stale "FORWARD rules on mpqemubr0"
     check (testing the wrong iptables backend — Multipass writes to
     iptables-legacy, that check reads nftables) and left the VMs as
     freshly-launched, unprovisioned images (no kubeadm/kubectl at
     all). Fixed the check to be informational instead of blocking.
  3. Did the normal `lab-management.sh rebuild --force` +
     `pipeline/main.sh`, which stalled entirely on `apt-get update`
     across all 4 nodes — real root cause: Docker's own nftables-
     backed FORWARD chain (DOCKER-USER/DOCKER-FORWARD) defaults to
     policy DROP and gets reapplied on every Docker daemon restart,
     silently killing all outbound internet from the Multipass bridge,
     independent of Multipass's own (correct) iptables-legacy rules.
     Fixed with an ACCEPT rule in DOCKER-USER (Docker's own documented
     insertion point for user rules), scripted as
     scripts/fix-network-access.sh and wired into lab-management.sh
     to run automatically, before VM launch (not after — cloud-init
     should always have internet from boot 1).
  4. With the cluster healthy again, revisited the Windows-direct-
     access problem that ADR-029 had abandoned back on 2026-07-18.
     Root cause turned out to be three stacked issues, none of them
     the asymmetric-routing/rp_filter theory originally suspected:
     the non-persistent Windows route (now scripts/windows/
     setup-route.ps1, idempotent + self-elevating), the same
     DOCKER-USER FORWARD-DROP bug from step 3, and — the one that
     really threw us off — `multipass list` reporting stale cached
     IPs after a rebuild, so early retests kept pinging a dead
     address. Ground truth came from `multipass exec <vm> --
     ip addr show ens3`. With all three fixed, direct HTTPS access
     from Windows to both Rancher and ArgoCD Gateway IPs now returns
     a clean 200 on /healthz. Decision: SSH tunnel stays the default,
     no-setup-required fallback (the fixes are non-persistent, reset
     every Windows/Docker restart); direct IP access is now a
     documented, working alternative once setup-route.ps1 and
     fix-network-access.sh have run for the session. Written up as
     the Resolution addendum on ADR-029.

Also: moved rancher-tunnel.sh/argocd-tunnel.sh into scripts/tunnels/
(fixed a REPO_ROOT path-depth bug this exposed), consolidated the
gateway_api namespace manifest into kubernetes/manifests/
gateway_api_metallb/, and rewrote README.md — status section, roadmap

=== Observability stack: kube-prometheus-stack via Helm, RAM reality check, main.sh redesign — 19:15 19-07-2026 ===
Chose kube-prometheus-stack (prometheus-community, chart 87.17.0) for
Prometheus + Grafana + Alertmanager — same package used at the day
job, matches ADR-030's Artifact Hub policy (ADR-031).

Before installing, checked actual RAM headroom: WSL2 host itself was
already tight (19GB total, ~17GB claimed by the 4 fixed-size VM
allocations, swap in use) — a separate, harder constraint than
in-cluster memory, since VM memory is reserved by KVM regardless of
what's running inside. In-cluster, scaling Rancher's deployment to 0
only freed ~400MB (most of its footprint turned out to be Fleet and
Rancher Turtles, sub-components it manages as independent Helm
releases, untouched by scaling the main deployment). Fully uninstalled
Rancher and ArgoCD instead — ArgoCD came out clean, Rancher left
several cattle-*/fleet-*/local namespaces stuck Terminating on
finalizers referencing controllers that no longer existed
(controller.cattle.io/*, wrangler.cattle.io/*, fleet.cattle.io/*),
cleared by patching each stuck resource's finalizers to empty.

Installed with resources tuned well below chart defaults (Prometheus
512Mi/1Gi, Alertmanager 64Mi/128Mi, Grafana 128Mi/256Mi, 24h retention,
ephemeral storage since there's no StorageClass in this lab) and the
kubeadm-only-127.0.0.1 control-plane ServiceMonitors (kubeControllerManager/
kubeScheduler/kubeEtcd/kubeProxy) disabled to avoid guaranteed scrape
failures.

Hit a real bug mid-install: the Grafana Gateway's self-signed TLS cert
kept failing "not yet valid" even well past its notBefore time.
Root cause: cp-2/w-1/w-2 (Envoy Gateway runs on worker-2) had their
clocks stuck ~20 minutes in the past under host CPU pressure, despite
`timedatectl` reporting "System clock synchronized: yes" — the daemon
trusted its last successful check rather than continuously verifying.
Fixed with `systemctl restart systemd-timesyncd` on the affected
nodes, then had to delete+recreate the Gateway object itself to force
Envoy Gateway to re-read the (already-correct) secret. Not yet
automated — added as a follow-up to extend morning-check.sh with a
per-VM clock check.

Real footprint after install: ~900MB-1GB total, leaving ~1.4-1.5GB
free on control planes and ~2.5-2.6GB on workers. Decided against
reinstalling Rancher/ArgoCD on top of that — too thin a margin on the
control planes specifically. Instead redesigned scripts/pipeline/
main.sh: after the cluster + Gateway API install, it now prompts
interactively for exactly one application (Rancher, ArgoCD, or
Observability) rather than chaining all three. This is the durable
working mode until the host gets more RAM later this year, not a
one-off workaround — documented as a follow-up on ADR-031.

=== Log aggregation: Loki + Grafana Alloy, wired into Grafana — 22:26 19-07-2026 ===
Closed out the observability stack with log aggregation. Loki (chart
18.4.4, note the repo moved to grafana-community/helm-charts as of
2026-03-16 — the old grafana/helm-charts location for this chart is
stale now) in SingleBinary mode, filesystem storage, no read/write/
backend/gateway/caches — same minimal-footprint shape as Prometheus/
Alertmanager. Grafana Alloy (chart 1.10.0) as the log shipper, since
Promtail hit EOL on 2026-03-02. Alloy collects logs via the Kubernetes
API (discovery.kubernetes + loki.source.kubernetes) rather than a
hostPath /var/log mount, so no privileged DaemonSet needed.

First snag: Alloy's DaemonSet only scheduled on 2 of 4 nodes — missing
a toleration for the control-plane NoSchedule taint. Fixed by adding
controller.tolerations to alloy-values.yaml.

Second snag, more interesting: after wiring Grafana to Loki via
additionalDataSources and confirming the datasource showed up fine,
Explore returned "no logs found" with a namespace filter, even though
Alloy's own logs showed it actively tailing pods. Root cause:
loki.source.kubernetes doesn't promote namespace/pod/container to
actual Loki labels by default — it only uses those meta-labels
internally to know what to tail. The resulting streams only carried
instance/job labels, so {namespace="monitoring"} matched nothing.
Fixed by adding a discovery.relabel component between
discovery.kubernetes and loki.source.kubernetes, explicitly mapping
__meta_kubernetes_namespace/__meta_kubernetes_pod_name/
__meta_kubernetes_pod_container_name to namespace/pod/container.
Verified in Explore afterward — 96 log lines, correct labels.

Also caught and fixed a real duplication bug in docs/decisions.md
while writing ADR-032: an earlier append had left ADR-031's
"Resolution" and "Known issue" notes duplicated back-to-back. Cleaned
up before adding the new ADR.

Folded the Loki + Alloy install into scripts/pipeline/06_observability.sh
(previously only kube-prometheus-stack) so the "Observability" choice
in main.sh's one-app-at-a-time prompt installs the full stack — metrics
and logs — in one go from a clean rebuild.

Status: full observability stack (Prometheus, Alertmanager, Grafana,
