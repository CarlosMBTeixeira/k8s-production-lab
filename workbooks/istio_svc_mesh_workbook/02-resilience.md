## 2.0 — The defaults nobody configured

```bash
P=$(kubectl -n bookinfo get pod -l app=productpage -o jsonpath='{.items[0].metadata.name}')
istioctl pc route "$P" -n bookinfo --name 9080 -o json \
  | jq -c '.[].virtualHosts[] | select(.name|startswith("reviews")) | .routes[0].route | {timeout, retryPolicy}'
```

> **Hypothesis.** With no VirtualService, the mesh neither times out nor
> retries — it is a transparent pipe.
>
> **Tool.** The command above.
>
> **Expected if right.** Half right. `timeout: "0s"` — **no timeout at
> all**: a hung upstream holds the caller forever unless the app has its
> own. But there **are** retries: `numRetries: 2`, `retryOn:
> connect-failure,refused-stream,unavailable,cancelled,retriable-status-codes`.
> And `retriableStatusCodes` is empty, so a plain **503 from the app is
> not retried** — only connection-level failures are.
>
> **What would have caught this sooner.** Reading Envoy's effective route
> instead of the VirtualService. The absence of a VirtualService is not
> the absence of policy.

## 2.1 — Fault injection: test a failure without breaking anything

```bash
kubectl apply -n bookinfo -f $B/bookinfo/networking/destination-rule-all.yaml
kubectl apply -n bookinfo -f $B/bookinfo/networking/virtual-service-all-v1.yaml
kubectl apply -n bookinfo -f $B/bookinfo/networking/virtual-service-reviews-test-v2.yaml
kubectl apply -n bookinfo -f $B/bookinfo/networking/virtual-service-ratings-test-delay.yaml
```

That injects a **7 s delay** on ratings, for user `jason` only. Log in as
jason through the Bookinfo tunnel and load the page.

> **Hypothesis.** The page takes ~7 s and then shows ratings.
>
> **Tool.** The browser, then the productpage and reviews sidecar logs
> for that request ID.
>
> **Expected if right.** Wrong — and this is the classic finding. The
> page returns in about **6 s with "Error fetching product reviews"**.
> productpage's call to reviews has its own timeout plus a retry in the
> application code (≈3 s × 2), which gives up before reviews-v2's call
> to ratings (hard-coded 10 s) gets its delayed answer. The injected
> delay exposed a **mismatch of timeouts between two services** — a real
> bug that only shows under latency. The ratings sidecar logs the
> request with flag `DI` (delay injected).
>
> **What would have caught this sooner.** Writing down the timeout chain
> end to end *before* injecting: caller timeout must exceed callee
> timeout × attempts. Faults are how you test that chain; production
> latency is the expensive way.

Then swap the delay for an abort:
`kubectl apply -n bookinfo -f $B/bookinfo/networking/virtual-service-ratings-test-abort.yaml`
→ HTTP 500 for jason, flag `FI` (fault injected). Note the request never
reaches the ratings container: the fault is generated by the **caller's**
sidecar.

## 2.2 — Timeouts: put one where the default is "forever"

```bash
kubectl apply -n bookinfo -f $B/bookinfo/networking/virtual-service-all-v1.yaml   # reset
kubectl -n bookinfo patch vs reviews --type merge -p '{"spec":{"http":[{"route":[{"destination":{"host":"reviews","subset":"v2"}}],"timeout":"0.5s"}]}}'
kubectl -n bookinfo patch vs ratings --type merge -p '{"spec":{"http":[{"fault":{"delay":{"percentage":{"value":100},"fixedDelay":"2s"}},"route":[{"destination":{"host":"ratings","subset":"v1"}}]}]}}'
```

> **Hypothesis.** Every page load now takes ~0.5 s and shows "Error
> fetching product reviews".
>
> **Tool.** `./scripts/mesh-break.sh check`, then productpage's sidecar log.
>
> **Expected if right.** Loads return in about **1 s**, not 0.5 s: the
> 0.5 s VirtualService timeout fires, and productpage's application-level
> retry tries once more. The sidecar line for each attempt shows `504 UT`
> (upstream request timeout). Two layers of retry — app and mesh — is the
> norm, and they multiply.
>
> **What would have caught this sooner.** Counting attempts per user
> request in the access log by request ID. If one user request shows
> two or more upstream lines, there is a retry layer you didn't know about.

## 2.3 — Retries: help, and amplification

Remove the timeout and the delay, then make ratings fail half the time
and add a retry policy on the caller:

```bash
kubectl apply -n bookinfo -f $B/bookinfo/networking/virtual-service-all-v1.yaml   # reset
kubectl -n bookinfo patch vs ratings --type merge -p '{"spec":{"http":[{"fault":{"abort":{"percentage":{"value":50},"httpStatus":503}},"route":[{"destination":{"host":"ratings","subset":"v1"}}]}]}}'
```

> **Hypothesis.** Adding `retries: {attempts: 3, retryOn: 5xx}` on the
> ratings route hides the 50% failure from users.
>
> **Tool.** Add the retries block to the ratings VirtualService, then
> `./scripts/mesh-break.sh check` (route reviews to v2 first so ratings
> is called) and the reviews sidecar's stats:
> ```bash
> R=$(kubectl -n bookinfo get pod -l app=reviews,version=v2 -o jsonpath='{.items[0].metadata.name}')
> kubectl -n bookinfo exec "$R" -c istio-proxy -- pilot-agent request GET stats | grep 'ratings.*upstream_rq_retry'
> ```
>
> **Expected if right.** It does **not** help — the fault is injected by
> the same sidecar that would retry, and fault injection is applied
> before the retry policy, so retries never see a "real" upstream 503.
> Faults test the *caller's* handling, not the retry policy. To see
> retries work, the failure must come from the upstream (2.5 uses httpbin
> for that). The lesson worth keeping: **know where a failure is generated
> before deciding which knob affects it.**
>
> **What would have caught this sooner.** The response flag. `FI` means
> "generated here"; a retried upstream failure shows `URX` when retries
> are exhausted.

## 2.4 — Circuit breaking: protect a service from its callers

```bash
kubectl apply -n bookinfo -f $B/bookinfo/networking/virtual-service-all-v1.yaml   # reset
kubectl apply -n bookinfo -f $B/httpbin/httpbin.yaml -f $B/httpbin/sample-client/fortio-deploy.yaml
kubectl -n bookinfo wait --for=condition=Available deploy/httpbin deploy/fortio-deploy --timeout=240s
kubectl apply -n bookinfo -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata: {name: httpbin}
spec:
  host: httpbin
  trafficPolicy:
    connectionPool:
      tcp: {maxConnections: 1}
      http: {http1MaxPendingRequests: 1, maxRequestsPerConnection: 1}
EOF
F=$(kubectl -n bookinfo get pod -l app=fortio -o jsonpath='{.items[0].metadata.name}')
kubectl -n bookinfo exec "$F" -c fortio -- fortio load -c 1 -qps 0 -n 20 -loglevel Warning http://httpbin:8000/get
kubectl -n bookinfo exec "$F" -c fortio -- fortio load -c 3 -qps 0 -n 30 -loglevel Warning http://httpbin:8000/get
```

> **Hypothesis.** At concurrency 3 against a limit of 1 connection + 1
> pending, about a third of requests fail, and httpbin sees and rejects
> them.
>
> **Tool.** fortio's `Code` summary; then **both** sidecar logs:
> ```bash
> kubectl -n bookinfo logs "$F" -c istio-proxy --tail=100 | awk '{print $5,$6}' | sort | uniq -c
> kubectl -n bookinfo logs deploy/httpbin -c istio-proxy --tail=100 | awk '{print $5,$6}' | sort | uniq -c
> kubectl -n bookinfo exec "$F" -c istio-proxy -- pilot-agent request GET stats | grep -E 'httpbin.*(cx_overflow|pending_overflow)'
> ```
>
> **Expected if right.** The rate is about right (on this lab: `c=1` →
> 100% 200; `c=3` → **60% 200, 40% 503**), but httpbin **never sees**
> the rejected requests. Its sidecar logs only 200s. The caller's
> sidecar logs `503 UO upstream_reset_before_response_started{overflow}`,
> and `upstream_rq_pending_overflow` counts them. The circuit breaker
> lives in the **caller**, configured by a DestinationRule on the
> **callee's** host.
>
> **What would have caught this sooner.** `UO` in the caller's log with
> no matching line on the callee. When the server says it never got the
> request, look at the client's connection pool.

## 2.5 — Outlier detection: ejecting a bad endpoint

```bash
kubectl apply -n bookinfo -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata: {name: httpbin}
spec:
  host: httpbin
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 1
      interval: 1s
      baseEjectionTime: 3m
      maxEjectionPercent: 100
EOF
kubectl -n bookinfo exec "$F" -c fortio -- fortio curl -quiet http://httpbin:8000/status/503
kubectl -n bookinfo exec "$F" -c fortio -- fortio load -c 1 -qps 0 -n 5 -loglevel Warning http://httpbin:8000/get
istioctl pc endpoint "$F" -n bookinfo --cluster 'outbound|8000||httpbin.bookinfo.svc.cluster.local'
```

> **Hypothesis.** After one deliberate 503, the next `/get` requests
> still succeed — `/get` is healthy, only `/status/503` failed.
>
> **Tool.** fortio, then `pc endpoint`.
>
> **Expected if right.** Wrong, and dangerously so. All 5 `/get` return
> **503 `UH` no_healthy_upstream**; `pc endpoint` shows httpbin's only
> endpoint `HEALTHY` but `OUTLIER CHECK FAILED`. Outlier detection judges
> **endpoints, not paths**, and with `maxEjectionPercent: 100` and one
> replica it ejected the whole service for 3 minutes. Production rule:
> never let outlier detection eject 100% of a small pool — keep
> `maxEjectionPercent` below it, or run enough replicas that one bad
> endpoint is a minority.
>
> **What would have caught this sooner.** `OUTLIER CHECK` in
> `pc endpoint`. Kubernetes still thinks the pod is ready; only Envoy has
> stopped sending to it — readiness probes and the mesh disagree, and
> only `istioctl` shows it.

Clean up: `kubectl delete -n bookinfo dr httpbin` and
`kubectl delete -n bookinfo -f $B/httpbin/sample-client/fortio-deploy.yaml -f $B/httpbin/httpbin.yaml`,
then `kubectl delete -n bookinfo vs --all` and `kubectl delete -n bookinfo dr --all`.

**Done when**
- One LogQL query over the session's window returns counts per response
  flag for bookinfo sidecars, and you can explain every flag in the
  result (`DI`, `FI`, `UT`, `UO`, `UH`):
  ```logql
  sum by (flag) (count_over_time({namespace="bookinfo", container="istio-proxy"}
    | regexp `" (?P<code>\d{3}) (?P<flag>[A-Z,]+) ` | flag != "" [30m]))
  ```
  Combined flags are normal: `URX,UF` means retries exhausted *and* the
  last attempt failed to connect. Without the `flag != ""` filter, every
  successful line (flag `-`, which the regex does not match) lands in an
  empty `{}` group and swamps the result.
- You can state, for the productpage → reviews → ratings chain, the
  effective timeout and number of attempts at each hop, and why the 7 s
  delay in 2.1 produced an error at ~6 s.
- `bookinfo` is back to no VirtualService, no DestinationRule, no
  httpbin/fortio.
